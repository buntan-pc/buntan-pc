# ベンチマークの実行命令数・サイクル数計測

`ucc/benchmarks/` の C コードを使い、コンパイラが生成するコードの性能を計測します。
現在の計測バックエンドは Verilator シミュレータです。

`+map=<mapファイル> +profile=<関数名>` を指定すると、その関数の最初の実行について、
実行を完了した命令数とクロック数を標準エラーに出力します。
`buntan_main` を指定すればアプリ本体、`fib` などを指定すれば特定の関数を測れます。
指定しなければ従来どおり動作します。

## ビルドから計測まで一括実行

`ucc/profile` を使えます（GNU Make 4.3 以降が必要です）。以下はリポジトリのルートからの実行例です。

```sh
./ucc/profile foo.c                 # buntan_main を計測
./ucc/profile foo.c func_name       # 指定した関数を計測
./ucc/profile -v foo.c              # 各コマンドとその全出力も表示
./ucc/profile ucc/benchmarks/fib.c fib
./ucc/profile ucc/benchmarks/othello.c
```

必要なコンパイラ・アセンブラ・シミュレータを Make でビルドした後、
`cpu/verilator/profile.mk` でソースをビルドします。

成果物はソースのあるディレクトリ内の `.profile/` に
`foo.s`、`foo.pmem.hex`、`foo.dmem.hex`、`foo.map` として生成します。
通常の Make の依存関係・更新日時判定により、最新なら再ビルドを省略します。
ヘッダの依存関係はホストの C コンパイラの `-MM` で `foo.d` に生成します。
関数名だけを変えた場合も再ビルドせず、map などが欠けた場合は再生成します。
DOS 用など別条件のビルドと混ざらないよう、計測用の出力先を分けています。
独自の JSON による更新判定は行いません。旧版の `foo.profile.json` は使用しません。

引数のソースパスはカレントディレクトリからの相対パス、または絶対パスで指定できます。
通常は途中のコマンド出力を隠し、計測結果を標準エラー、プログラムの結果を標準出力に表示します。
`-v`（`--verbose`）指定時は各コマンドと全出力も表示します。
`--max-cycles <上限>` でシミュレーション全体のサイクル上限を指定できます。
省略時は10,000,000サイクルを使います。
このオプションは `CLOCK_HZ` や周辺機器のタイミングを変更しません。

シミュレーション中は約1秒（ホスト上の実時間）ごとに、実行済みサイクル数を
`progress: 655360 cycles` のように標準エラーへ1行ずつ出力します。
1秒未満で終了した場合は進捗行を出力しません。

コマンドが失敗した場合は、`-v` の有無にかかわらず、そのコマンドと出力を表示します。
ビルドが失敗した場合はシミュレーションを実行せず、シミュレータの終了コードも伝播します。
対象は DOS に依存せず単体起動できるコードです。

## フィボナッチの計測例

以下はリポジトリのルートから実行します。G++、Verilator、Make、Python 3 が必要です。

```sh
make -C ucc
make -C uas
make -C cpu/verilator
bench_dir=$(mktemp -d /tmp/buntan-fib.XXXXXX)
ucc/cc -o "$bench_dir/fib.s" ucc/benchmarks/fib.c
uas/as --pmem "$bench_dir/fib.pmem.hex" --dmem "$bench_dir/fib.dmem.hex" \
  --map "$bench_dir/fib.map" "$bench_dir/fib.s"
cpu/verilator/obj_dir/Vsim_top \
  +pmem="$bench_dir/fib.pmem.hex" +dmem="$bench_dir/fib.dmem.hex" \
  +map="$bench_dir/fib.map" +profile=buntan_main
```

標準出力の `08` は従来と同じプログラムの計算結果です。
標準エラーには、初期化に関するメッセージに加えて次の形式の計測結果が出ます。

```text
profile_function: buntan_main
profile_status:   complete
instructions:     ...
clock_cycles:     ...
hardware_time:    ... us (clock=27MHz)
```

`+profile=fib` に変更すると、最初の `fib(6)` 呼び出しについて、再帰呼び出しを含む
全体を測ります。`fib(5)` などの内側の呼び出しが戻っても計測は終わりません。

## 数値の意味と計測区間

- `instructions`: 対象関数の先頭命令から、呼び出し元へ戻る `ret` までに完了した命令数。
  呼び出し元の `call` は除き、内部の関数呼び出し、再帰、NOP、分岐、メモリアクセスを含みます。
- `clock_cycles`: 先頭命令の取得から最後の命令完了までのクロック数。
  起動処理、復帰後の UART 送信、送信完了待ちは含みません。
- `hardware_time`: 実機のクロックを27 MHzとして `clock_cycles / 27,000,000` で計算した
  実機での実行時間（実測値ではありません）。`(clock=27MHz)` を併記します。シミュレータの設定周波数やホスト上の処理時間とは別で、
  値に応じて `ns`、`us`、`ms`、`s` を選び、小数点以下3桁で表示します。
- 計測中の割り込みハンドラの命令も含めます。ハードウェア割り込みへの移行で
  実行を抑止された命令は数えませんが、その移行に使うクロックは含めます。
- 同じ関数が後で再び呼び出されても、最初の結果を保持します。
  計測が完了してもシミュレーションは継続し、従来の UART 出力条件で終了します。

`profile_status` は次の3種類です。

| 状態 | 意味 |
| --- | --- |
| `complete` | 関数が復帰し、計測が完了した |
| `not_entered` | 対象関数を実行せずに終了した。数値は0 |
| `incomplete` | 関数が復帰する前に終了またはタイムアウトした。数値は途中経過 |

シミュレータの終了コードは従来と同じで、UART による終了が0、タイムアウトが2、
入力エラーが1です。比較には `profile_status` が `complete` の結果を使ってください。
`+max-cycles=<上限>` は従来どおりシミュレーション全体の実行上限を指定します。
シミュレータ単体の既定上限は `CLOCK_HZ` サイクルです。
`ucc/profile` はこれを10,000,000サイクルで上書きします。
`+progress` を指定すると、約1秒ごとに `progress: 実行済み cycles` を標準エラーに出力します。
`ucc/profile` は常にこのオプションを指定します。

map は必ず計測する命令イメージと同じアセンブルで生成してください。
対象名が `.text` にない、重複する、アドレスが不正、map を読めない場合は実行前にエラーになります。
map の関数名と一致するラベルへの到達を入口とみなすため、インライン化・削除された関数は
測れません。その場合は残っている外側の関数を指定します。
関数内の任意の2地点、複数回の集計、非標準の制御移動による関数脱出は対象外です。

## コンパイラ変更前後の比較

同じソース・入力・対象関数を使い、変更前後それぞれのコンパイラで
コンパイル、アセンブル、計測を行います。計算結果も一致することを確認します。
計測結果を保存する場合は、実行コマンドの末尾に `2> before.log` などを付けます。
`-v` でログも含めた場合は、`rg -A 4 '^profile_function:' before.log` で取り出せます。

命令数の削減率は `1 - 変更後の instructions / 変更前の instructions` です。
現在の CPU は1命令を4フェーズで処理するため、割り込みがなければ
`clock_cycles = 4 × instructions` となります。CPU 計算主体の処理を同じ条件で比べる指標として使い、
周辺機器の待ち時間を含む実機の所要時間とは区別してください。
クロック周波数はビルド時の `CLOCK_HZ` で決まり、既定値は100,000 Hzです。

## ベンチマーク履歴の記録と閲覧

```sh
./ucc/benchmark                  # 必要な場合だけ全対象を計測・記録
make -C ucc benchmark            # 同じ操作
./ucc/benchmark --force          # 変更がなくても再計測
./ucc/benchmark --show abc1234   # 指定コミット以前の直近の計測結果
./ucc/benchmark --log            # 計測値が変わったコミットを古い順に表示
./ucc/benchmark --log abc1234    # 指定コミットまでの履歴
./ucc/benchmark --log --all      # 値が変わらなかったコミットもすべて表示
```

対象のファイルと関数は `ucc/benchmarks/targets.json` で管理します。
`source` はこのディレクトリからの相対パスです。同じソースの複数関数も登録できます。

```json
[
  {"source": "fib.c", "function": "fib"},
  {"source": "othello.c", "function": "buntan_main"}
]
```

コンパイラ・アセンブラの C ソース、ヘッダ、Makefile、ベンチマークの C ソースと
ヘッダ、対象一覧、CPU の RTL、Verilator の実装とビルド設定、計測スクリプトを
変更検出の対象にします。未追跡のソースも含め、ファイルの追加・削除も検出します。
ドキュメント、テスト、生成物、履歴ファイル自体の更新では再計測しません。
対象パスの定義は `ucc/benchmark` の `watched()` にあります。

結果は `ucc/benchmarks/profile-history.json` に記録します。
全対象が正常終了し、計測中に入力ファイルが変わっていない場合だけ更新します。
タイムアウトやコンパイル失敗時は既存の履歴を保持します。
`--max-cycles` で各対象の上限を変更できます（既定10,000,000）。

コンパイラなどの変更と、対象一覧・対象コード・ヘッダ・更新された履歴を
一緒にコミットしてください。コミットやステージは自動では行いません。

- `"HEAD"` には作業中の計測結果を置きます。`base_commit` は計測時の作業元コミットで、
  作業中の結果をそのコミットに対する結果として扱うものではありません。
  値が同じでも再計測を含むコミットを識別できるようにするための情報です。
- 次の計測時に、コミット済み履歴の結果を、それを記録したコミットハッシュへ対応付けます。
- 同じ入力で繰り返し実行した場合は、計測も履歴の書き換えも省略します。
  判定用キャッシュは Git 管理外の `.profile/benchmark-state.json` に置きます。
  キャッシュがなくても、直近のコミット済み計測時点と入力が同じなら省略できます。

`--show` と `--log` は作業ツリーの未コミット結果を使いません。
指定したコミットから第一親の履歴をさかのぼり、結果が記録されたコミットを探します。
別ブランチの結果を取り違えず、計測を省略したコミットにも直近の結果を表示できます。
指定コミット以前に記録がない場合はエラーになります。

`--log` は最初の計測と、命令数・サイクル数が変わったコミットを表示します。
対象の追加・削除も変化として扱います。値が同じだった区間は
`… (N commits skipped)` と表示します。`--all` では各コミットについて結果を表示し、
`*` は計測結果を記録したコミット、`=` は直前の結果を引き継いだコミットを示します。
コミット日付とメッセージ、各値と直前の結果からの増減も表示します。
コードや CPU 自体の変更も値に影響するため、コンパイラ最適化の比較時は変更内容も確認してください。

## 検証

```sh
make -C cpu/verilator test-profile
make -C ucc test-benchmark
```

一時ディレクトリでテスト用プログラムを生成し、実際の CPU RTL で検証します。
手計算できる命令数、分岐・ループ、再帰・間接呼び出し、FP の退避、
ソフトウェア／ハードウェア割り込み、未到達・未完了、map の不備、
フィボナッチの計算結果と再現性を確認します。
